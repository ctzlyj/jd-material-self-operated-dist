# Authorized dual-key generation with bounded response recovery

Use only after explicit production authorization for both runtime credentials and failure skipping. `run-direct --dual-key-images --no-generation-retries --defer-incomplete --defer-readback` selects this mode. Require total image concurrency four. Read credentials from `JD_LLM_API_KEY` and `JD_LLM_API_KEY_2` in the secure process environment; never print or persist them. A missing or duplicate secondary credential fails closed. Single-key defaults, manual mode and POP are unchanged.

One shared model client reserves two in-flight slots per key, shares the existing one-start-per-second gate and primary text client, and shares quota, authentication and cancellation stops. A request never changes credentials. Text has one HTTP attempt; invalid generated text is not regenerated. Images have one attempt except for the strictly bounded interrupted-response recovery in `image-transport-retry.md`: the same image request may be retried once after five seconds, never on a different key or with changed content. Original valid-image caches, complete SKU membership, field exclusions and rejected-image markers remain authoritative. The diagnostic comparison does not by itself authorize production or establish a speed multiplier.

The dual-key dispatcher also spaces starts for the same key by at least two seconds, while retaining the shared global one-second gate and total four/per-key two concurrency caps. This conservative local pacing avoids adjacent same-key bursts observed near one second; it is not a claimed provider threshold or a proven explanation for every 2008 response. Recheck both intervals after cooldown or key-specific waiting, so delaying one key cannot bunch subsequent global dispatches. Keep the normal global cooldown and no-retry policy if throttling persists. Compare real valid-image throughput, failure rate and cooldown cost after rollout rather than claiming a speed gain from offline timing tests.

Ordinary terminal image failures are recorded by exact prompt/model/reference fingerprint and skipped, including after restart. Successful image decoding and HTTP success are separate outcomes. Queued cancellation is not a failed API call. Native authentication and exhausted quota stop both credentials. A content-policy resource ban retains the existing stop rather than trying another image or credential; do not combine this mode with `--resource-cooldown`, whose same-request probes contradict terminal failure skipping.

For HTTP 429 other than explicit quota exhaustion, skip the failed request and cool **both** credentials. Prefer a valid finite nonnegative numeric or HTTP-date `Retry-After`, without adding a local five-minute floor; the global and same-key start gates still apply even when the server specifies zero. If the header is missing, invalid, negative or non-finite, wait 60 seconds initially and 120 seconds on further unavailability. A failed recovery task without a new 429 waits 120 seconds; a new 429 already defines its own cooldown and must not receive a second fallback delay. Keep an immutable thirty-minute deadline from the first rejection, including across restart. After cooling, allow just one next original task, not a retry or altered substitute for the failed image. Each blocked credential requires its own valid new-image proof; older in-flight successes and HTTP 200 with invalid image data do not resolve the episode. Continued unavailability stops at the original deadline. No credential bypass, extra concurrency or automatic reopening of an exhausted episode is allowed.

An upgrade never shortens an already persisted `nextStartAt` or resets its first rejection/deadline: older state may contain a longer server-required wait. The new policy applies to newly observed throttles and retains the greatest existing wait. Evidence records `cooldownPolicy`, `cooldownDelaySource`, `cooldownDelaySeconds` and `cooldownUpdatedAt` to distinguish server instructions, initial/subsequent defaults and failed-recovery delays. This optimization changes unnecessary waiting, not the model's response latency, generation concurrency, failure replay policy or maintenance authorization.

Evidence in `.state/dual-key-generation` contains UUID attempt IDs, key slot numbers, exact request fingerprints, sanitized failures, wall times and cooldown episodes, never keys or image payloads. Use actual dispatched attempts, valid generated images and recovery wall time separately. Normal product-value readback remains final-only, but unknown uploads/bindings/titles still require immediate reconciliation or stop, never replay.

Text-format failure diagnostics report the actual configured generation attempts: one under no-generation-retries, three under the compatible default. Check actual calls separately from validation failures. Older cached errors can still say three despite an original one-attempt run; preserve those receipts rather than rewriting history or inferring retries from the old wording. This diagnostic correction does not change validation, generation, retry policy or image dispatch.

Recovery belongs to the credential that was rejected: track every blocked key slot and require a valid new original-task image from each of those slots after the global cooldown. Another key's success must not clear an unresolved key or start a fresh thirty-minute window on its next rejection. Continue serial dispatch until all blocked slots have their own success proof. Legacy cooldown states without slot attribution are archived byte-for-byte and reconstructed only from their original response evidence and valid-image attempts; missing evidence stops rather than trusting the old resolved flag. Preserve the original first rejection and deadline, and never reopen an exhausted state automatically.

Regression: `tests/test_dual_key_generation.py` exercises two slots per key, the shared gate, one-attempt failures across restart, global cooldown and immutable deadlines, hard stops, cancellation, invalid bodies, secret redaction, primary-only text and CLI integration. Apply non-destructively with the existing installer only after the current writer settles and unknown product writes are checked. Keep `.install-baseline.json` and `.merge-candidates`; never overwrite divergent installed files. Offline proofs do not establish actual product binding, audit approval or refreshed scores.
