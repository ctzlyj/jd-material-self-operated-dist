# Current visible SKU reductions

Use `run-direct --current-visible-skus` only after the user explicitly authorizes processing currently visible SKUs instead of insisting on historical counts. Default execution still requires the frozen membership. This option applies to the same ERP, owner filter and named SPUs; it does not expand into new products or new SKUs.

The native selected product list must return the exact SPUs, authenticated ERP and per-product declared counts. The full SKU endpoint must succeed without duplicates, unknown IDs or missing rows, and its counts must agree. Zero rows do not count as completion. Query errors are not reductions. Confirmed missing SKUs are recorded separately, never reported as maintained.

The runner preserves the direct plan, canonical child plan, source images, uploaded URLs and manual field exclusions. It records immutable `.state/scope-revisions/<id>/revision.json` evidence and a SHA-bound `.state/scope-revision.json` pointer. A cached task is archived byte-for-byte before updating its execution signature and projecting only its short-title fields. Activation is restartable after interruption. No image is deleted or regenerated by this transition.

The revised result includes the retained SKU IDs, SKU/title pairs, source rows, representative SKU and the intersection of already authorized short-title fields. Generation, binding requests, pre-write scope verification and final readback all use that same result. Reports reference the revision hash. The original failure ledger retains historical full SKU rows; removed/current membership remains explicit in the revision evidence.

Unknown uploads or writes still require reconciliation. Do not revise a changed SPU that already has product write receipts or frozen requests: preserve and reconcile those exact payloads instead of changing a request's SKU set. Existing unchanged-SPU receipts and valid images remain reusable. Omit the option to disable further reductions; saved revisions remain authoritative for their already-authorized execution, not silently reverted to the old membership.

Validate with `test_scope_revision.py`: successful reduction, default strict mode, incomplete/duplicate/empty/foreign SKU and ERP failures, cache preservation, interrupted activation, unknown/accepted write protection, generation projection, SHA tampering and final readback membership. Full source and clean-install suites remain required. Offline tests alone do not establish a live product write or audit approval.
