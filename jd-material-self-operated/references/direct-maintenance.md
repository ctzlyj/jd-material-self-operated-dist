# Explicit direct maintenance

Default business-failure policy is skip-and-report, not automatic repair. The direct CLI enables `--defer-incomplete` and `--no-generation-retries`; first use also selects one-attempt generation. A known failed SPU stays deferred across normal resumes; do not select `--repair-segment`, clear a failure marker, re-upload or create a fresh retry task without a specific correction request. Fresh plans hold native rejected SPUs unless the named repair exception is frozen. Retain valid images/URLs and every sibling SKU. Immutable reports include concrete upload/preflight/title rejection reasons in `failureReasons`, which flow into the complete-SKU CSV for colleague appeal. Unknown writes, quota/authentication and scope failures keep their original stop/reconciliation rules. This policy does not authorize resuming a paused task.

For explicitly requested final-batch verification, `--defer-readback` and `verify-direct` override only the normal successful post-write readback timing described below. See `final-readback.md`. Unknown writes still require immediate reconciliation.

Audit-rejected materials remain unfinished regardless of earlier API acceptance. New repair plans retain platform reasons and old URLs, reuse compatible approved companions, and refuse an unchanged rejected value even without a local receipt. See `rejected-materials.md` for the explicit delegated-target entry and correction requirements; a pending readback still is not audit approval or information-score refresh.

## Optional pooled image transport

`run-direct --image-transport direct-http` and `maintain-self-operated --image-transport direct-http` use the native image-space API with TLS verification, five pooled connections and no automatic write retries. The default remains `browser`; POP and manual delivery are unchanged. ERP/profile verification selects the existing background Browser Bridge context. Exact-host image-space cookies stay only in process memory, never in task files, command arguments or logs. The existing bridge cookie command is reused; no foreground tab or alternate credential store is involved.

All batch files must match durable intent SHA values before any upload request. Each upload rechecks image-space ERP, then sends the original native payload once. Unknown responses stop new dispatch, retain in-flight outcomes and flow into the original reconciliation ledger; never fall back to browser upload after an uncertain HTTP result. Keep accepted receipts even when an immediate image query has not caught up. For a newly accepted exact filename, query at most five times with one-second intervals, without resubmission. Native page/total metadata is preserved for the existing completeness checks. Connections close at the runner boundary; another ERP or profile cannot reuse them.

Regressions: `test_image_space_http.py` covers file hashes, identity, redirects, uncertain single dispatch, delayed readback, native paging, CLI opt-in and durable intent-to-restart reuse. `test_direct_pipeline.py` covers cleanup after success and unknown writes. Before full rollout, verify existing URLs read-only, then an authorized 1-SPU and 10-SPU production slice; offline tests and upload-only benchmarks do not prove product binding or information-score refresh. Switching transport does not relax any blocked product scope.

If the next segment's native SPU/SKU membership check fails during lookahead preparation, retain its frozen plan and stop before generating or writing that segment. The already-generated current segment may finish only through its existing independent ERP/full-SKU pre-write validation, request freezing, unknown-write guards and exact readback. Persist its receipt first, then surface the original scope error and stop the queue. This prevents a future scope failure from stranding unrelated ready images; it does not exclude the changed SPU, shrink its sibling set, or continue past the scope blocker. Authentication, unclassified validation, read/transport and uncertain-write errors still stop immediately. `test_direct_pipeline.py` and the actual-runner case in `test_first_use_execution.py` cover both the safe boundary and non-deferrable failures.

For a new colleague without a historical handoff, use `maintain-self-operated` and read `first-use.md`. It discovers only the authenticated ERP's own inventory, freezes a v2 direct plan, automatically advances through one/ten/remaining stages and aggregates inspection plus execution failures. The legacy v1 handoff/exclusion path below remains unchanged; never fabricate it for a fresh task.

Archive regression assertions resolve both paths before checking containment, including equivalent unresolved and Windows runner temporary paths. Keep the exact archived bytes and SHA checks; path normalization must not replace either evidence check or relax production scope validation.

On an authorized restart, a prior top-level progress error is archived byte-for-byte with a SHA-bound reference in the new run event before it is removed from the current status. A later error remains current and still stops the runner. This prevents a healthy resumed writer from appearing blocked by an old browser error; it does not clear upload, binding, title, resource or failure ledgers. Judge liveness from the process/session, not an old error or the historical `lastRun`. Activate upgrades only at a safe checkpoint with the previous writer stopped and unknown writes reconciled. `test_direct_pipeline.py` covers live-phase status, original error preservation, a new unknown-write failure and clean runs.

A user-requested checkpoint pause propagates to the shared model cancellation event before further image dispatch. Cancelled prefetched requests retain partial caches and are not permanent image failures. Let in-flight browser writes settle, verify their receipts and wait for the worker to exit; never kill the writer merely to speed up a handoff. Preserve the frozen prefetched group for the next explicit resumption.

A restarted resource window remains unresolved even when generation returns normally with only cached fields or swallowed per-SPU resource pauses. Reconstruct the exact frozen request and obtain the existing recovery probe's verified result before treating the resource as restored. Missing original request data stops safely without clearing the window or resetting its deadline. Cached-only delivery is never resource-recovery evidence.

## Bounded live scope reads

`run-titles` can start from a newly frozen direct plan before any image run. It uses an empty in-memory material checkpoint, retains source holds and all SKU reservations, and does not fabricate completed material progress. A missing material progress file alongside full-run events or segment receipts is not a new task: stop for reconciliation instead of silently resetting it. Existing title-only receipts remain SHA-checked and reusable when the full runner has never started.

For a user who explicitly authorizes up to half an hour of resource recovery, combine `--resource-cooldown --resource-cooldown-window 1800`. This waits five minutes and then ten minutes between isolated probes, bounded by thirty minutes from the original first rejection. The default remains 300 seconds with 60/120-second waits. Extending an existing exhausted five-minute episode archives its original bytes and SHA, preserves its request hash and first rejection time, and never restarts an already elapsed thirty-minute window. Only the same credential and exact blocked request can be probed; a valid recovered image is cached. Do not start another task or change keys to reset a resource block. Cached-only binding and title-only work can continue without image calls; neither is evidence that image resources have recovered. Keep quota, authentication, cancellation and unknown-write stops unchanged.

The direct image-space client groups up to ten planned lookup queries into one browser command, with at most five native reads in flight after ERP verification. It reuses the unchanged single-query bridge and pagination validator: only first pages are prefetched, further pages retain the existing checks. Missing or mismatched query results stop before upload intents are written; an errored read group drains in-flight reads without dispatching more work. Already verified URLs still require no lookup. This changes only pre-upload lookup scheduling, not image upload, byte-hash reconciliation, binding or the single-dispatch transport. The manual client and POP retain their existing lookup routes. These are local batch bounds, not official service limits; measure equivalent queries before claiming a speed gain.

The direct product bridge overlaps the existing five-SPU read group instead of querying its SPUs serially. It preserves request order and all sibling rows, verifies ERP before dispatch, and rejects duplicate, empty or oversized groups. Every in-flight read settles before a failed group returns an error; partial results never authorize writes. Native schema and complete-SKU checks remain unchanged. This only changes independent read scheduling, not binding/title writes, post-write verification, browser transport retries or image concurrency. Five is the chosen local bound, not a measured official service limit; compare equivalent live scopes before reporting speed gains. The default manual bridge and POP are unchanged.

## Measured stage durations

Upload intent and receipt `transport` now distinguish `self-operated-direct-http-sff` from `self-operated-browser-sff`. Earlier releases used the browser label for both routes; retain old immutable receipts and use the frozen execution option as separate transport evidence rather than rewriting history. This corrects telemetry only, not upload dispatch, idempotency or retry behavior.

New completed segment receipts include `stageSeconds` alongside `elapsedSeconds`: initial ERP/SKU scope verification, cache migration, generation, image upload, binding preparation, pre-write scope verification, binding with native readback, short titles with readback, and final local verification. Generation includes reference downloads and local exports; upload includes its local readiness and unknown-receipt checks. These are wall-clock stage durations, not isolated HTTP latency or official throughput limits. There are no additional business queries or writes. Keep the timings in the immutable SHA-bound report and compare equivalent workloads before claiming an optimization; missing timings in older reports mean unmeasured, not zero. Interrupted segments do not have a completed timing breakdown, and timings never change success, pending, rejection or unknown-write classifications.

## Short-title-only continuation

When an image resource restriction interrupts a segment after other SPUs have valid cached materials, use `run-direct --cached-only --limit <at-most-50> --defer-incomplete` for that existing active segment, or explicitly select a persisted `--repair-segment`. This bounded mode makes no model calls or reference downloads, retains the resource-pause evidence, uploads only complete valid material sets, and reuses frozen titles and write receipts. All ERP/full-sibling, payload, unknown-write and exact-readback guards remain. It never advances into new unattempted segments, never marks missing images as permanently skipped, and never changes the original plan or exclusions. Incomplete SPUs remain deferred; after provider resolution, repairing the same segment can reuse its successful fields without replaying accepted requests. Do not use this mode to probe a blocked model resource or claim the original scope is complete.

For read-only reconciliation, `verify_product_scope` returns the exact live SKU rows used for the unchanged inventory and full-sibling membership checks. Reuse those rows through `direct_reconcile.verified_title_rows` instead of querying the same titles again. This is same-observation reuse, not a persistent cache or permission to skip post-write readback. Legacy clients returning no rows keep the original fresh-query path. Missing SPUs, duplicate SKUs and changed membership still fail closed.

Use `run-titles` with the existing direct plan, ERP, confirmation token and `GENERATE_UPLOAD_BIND_AND_VERIFY` authorization when image generation is unavailable. This command does not make image requests, upload images, bind materials, or create import tasks. It reuses the existing text model, five workers, exact original-value conflict guard, title writer, immutable write attempts and readback. Within each segment, pending titles share model batches of up to 50 SKUs across SPUs; responses must match the exact requested SKU set before being saved under their original owners. Begin with one SPU, then ten before omitting the limit. A new total image budget is not inferred from a daily service quota.

The SHA-bound `title-only-plan.json` reserves full original SPU groups under the normal canonical segment directories; it does not edit the direct plan or manual exclusions. `title-only-progress.json` records attempted title fields separately, including native rejection and accepted-but-not-yet-visible values. It never adds SPUs to the main completed or deferred lists. The main `run-direct` entry resumes reserved groups intact, so existing title text and accepted, rejected or unknown receipts are reused rather than regenerated or replayed. Material work and every sibling SKU remain in scope. Both modes share the task lock and checkpoint control; finish or reconcile an active full segment before starting title-only work. Unknown writes, changed scope, authentication failure and real quota exhaustion still pause execution.

When explicitly asked to skip failed generation and continue, use `run-direct --defer-incomplete`. Known per-product failures are deferred without stopping later segments. Do not use titleless or alternative-reference regeneration for failed images in this mode. Preserve successful image files; a persisted `skipped_image_generation` marker prevents retry of the missing images. This flag does not change the default manual runner's failure threshold.

In this skip mode, an image HTTP 400 containing a policy rejection is terminal even when wrapped in `FAILED_RESPONSE`: do not classify it as a transient gateway failure and repeat the same rejected request. Ordinary transient failures retain bounded retries and the existing rate limiter. This is error classification, not a new visual or semantic review stage.

A provider `Forbidden` error stating that its resource is temporarily blocked for content policy is a service-level restriction, not a per-product rejection or user-key quota. Stop later image dispatch, preserve successful outputs and record `model_pause.reason=image-resource-blocked`; do not permanently mark all untouched products as generation failures. Do not rotate keys, switch provider resources or repeatedly probe the restricted service. Resume new image generation only after the provider resolves the restriction. Already cached work may be completed without model calls in an explicitly bounded segment; this does not reduce the original remaining scope or count image-incomplete SPUs as complete.

Resource pauses also retain HTTP status, full sanitized response data and allowlisted request-ID headers in `model_pause.evidence` and an append-only `.state/model-failures` record within the batch. `evidencePath` and `evidenceSha256` identify the durable record; it survives a successful resume that clears the transient pause. Nested serialized errors are redacted for credentials and image data without truncating later request IDs. A later blocked dispatch reuses the first evidence without another request. This adds no diagnostic probe, retries or resource switching. Older generic failures with no captured body still have unknown upstream IDs; never substitute a successful diagnostic ID for a failed request.

The direct runner still stops on quota exhaustion, authentication failure, failed native readback, identity/scope changes and new unknown upload/binding/title receipts. Unknown writes must be reconciled without replay. Accepted but not yet visible values are pending, not verified success. Deferred products never enter the completed set or disappear from the frozen scope.

An explicitly read-only browser query may retry `command_result_unknown` once, on the same dedicated session and without navigation. The single-dispatch transport remains unchanged. A second unknown result or an explicit identity/permission error stops; uploads, binding and title writes never use this read recovery. This handles lost read responses without misclassifying them as uncertain product mutations.

At a safe stop or end, `.state/failure-index.json` and `失败与待核实SKU清单.csv` list failed, previously held, awaiting-readback and interrupted items separately, with all sibling SKUs and source receipt hashes. Unattempted SPUs are counted separately, not labelled failures. `finished-with-failures` means every original SPU has been accounted for, not every SPU succeeded. A limited run with unattempted scope remains `checkpoint`.

Use only after the user explicitly authorizes generation, image upload, material binding and required short-title writes. A previous manual-only plan never becomes a direct plan by editing its hash or mode. `plan-direct` freezes a new contract against the original handoff and per-field exclusions. Original manual takeovers stay excluded; later workbook-ready images are reused but do not reduce the API-binding scope.

The direct client is independent of the default manual client. Verified binding algorithms and bridges are vendored with `DIRECT_BINDING_PROVENANCE.json`; no runtime imports refer to a mixed repository or another local checkout. Preserve the pinned safe WebCLI transport and its non-destructive upstream merge mechanism.

Before execution validate ERP, owner scope, complete sibling SKU membership, original queue and exclusion SHA values, source plans and source receipts. Source binding intents and receipts migrate with hashes. Required titles migrate field-by-field; excluded titles never enter the direct writer. Conflicting old fingerprints stop migration. Unknown submissions reconcile through exact readback only; never clear an intent or reset a directory to force resubmission.

Persist canonical desired bodies and actual request bodies before dispatch. Once a field has a desired value it cannot change silently; a previously incomplete field may be added within the same frozen scope, with an append-only desired-history record. Image binding intents are durable before dispatch and use the single-dispatch safe browser transport. Short-title writers record exact requests, native acceptance and after-values. No second human confirmation is needed for the already-authorized scope.

`direct-result.json` records all requested material types, complete SKU coverage, exact readback and platform audit states. An old pending image with a different URL is not this run's success and does not suppress a normal authorized binding request. Match the desired image across every sibling SKU; exact pending values suppress duplicate submission. A mismatching pending image can enter the existing official replacement path only without an accepted matching fingerprint or unresolved intent. Native rejection or an uncertain response remains a stop/reconciliation condition, never permission to force, cancel audit, or retry blindly. Accepted but not yet visible values remain unresolved. Exact values in pending audit are persisted, not approved or evidence of a refreshed information score.

Sequential segments reuse one browser client and a lazily initialized model client. The model client preserves the inherited four-image-worker, one-start-per-second gate across segments. Metrics count actual request paths and response statuses without headers, credentials or bodies. These settings are client limits, not measured official capacity. Reuse valid bitmaps and confirmed URLs; never add semantic review or an invented generation-call cap.

A native audit rejection of the exact desired material is a failure even if its submission was previously accepted. A failed readback query is also a failure, not evidence of propagation delay. Only accepted values that are not yet observed, without an explicit rejection or readback error, can be classified as awaiting readback. Keep the accepted receipt to prevent resubmission; never regenerate, alter the desired payload, or clear the receipt merely to hide an audit refusal.

Validate one SPU then ten before scaling. Segment reports, progress and source receipts are hash-verified on resume; segment state cannot move between ERP identities or directories. More than twenty percent actual failures within a segment pauses at its boundary. Exact accepted writes awaiting readback remain incomplete but do not count as failed submissions. This distinction follows a reproduced live short-title readback delay, not an assumption that acceptance is completion. Real quota exhaustion, identity changes, inconsistent scope or an uncertain exception preserve active work and stop. Failures remain in the original scope, not marked complete.

Known model content-policy failures from the SHA-bound source are held separately without resubmitting them. Preserve every affected SKU and do not bypass policy, login or quota restrictions, or swap credentials to evade them. Category-deletion rejections are business failures, not permission to move products into other categories.

Use `scripts/direct_reconcile.py --erp <erp> --output-dir <direct-run> --confirm-token <token>` for separate background read-only reconciliation. It freezes source receipt hashes and records exact new evidence without changing progress or old receipts, so it can inspect already-deferred SPUs while the main worker advances unrelated segments. Never interpret its output as a new write. A `.state/control.json` file with `action` equal to `pause` requests a safe stop before the next segment; `run` permits continuation. Do not delete locks or kill a process during a product write to upgrade the Skill.

After reproducing and fixing a generation defect, `run-direct --repair-segment <existing-segment-key>` resumes that exact frozen segment under the same lock and scope. It reuses images, URLs and native accepted/unknown receipts, and never resets a rejected or uncertain payload. Original result files remain immutable; a repair writes a new receipt under `direct-results` and archives the prior progress entry. Progress is recalculated from the current hash-bound segment receipts. This is not permission to retry content-policy failures or to change a desired field.

The binding executor persists its immediate uncached native readback with a byte SHA. The coordinator applies its exact-value verifier to that same evidence instead of querying every SPU a second time. Acceptance, fingerprints and all SKU values remain separately checked. A live larger segment exposed redundant detail reads; do not call larger batches faster without measuring their wall time. Existing selling-point checks now allow the verified physical action `对折挤水` while still rejecting `全场对折` and discount combinations; this removes a false positive and adds no new semantic review.

Short-title before/after reads include only SPUs owning a desired, still-authorized title field, while retaining all siblings within those SPUs. A live two-title segment previously read all fifty SPUs twice; querying unrelated SPUs was unnecessary. Whole-segment identity and SKU membership checks before writes are unchanged. Raw attempt totals must include immutable initial and repair receipts; current completion comes only from the progress ledger's current receipt for each segment.

Load original short-title values from the SHA-bound source plan, checking every pending SKU and SPU owner. Pass those original values to the existing writer's conflict guard and include them in the exact write-attempt snapshot. A current title may equal the original value or the desired value; a different human edit stops before title submission. Missing original evidence is not an empty title. The direct entry previously omitted this existing guard; synthetic conflict regression now proves zero writes, and historical real request audits must be checked separately rather than assuming a past overwrite occurred.

The direct workflow isolates a changed title to its entire SPU: preserve all siblings and current values, save original/current/desired conflict evidence, and omit that SPU from dispatched title bodies while other authorized SPUs continue. The conflict remains incomplete and is never counted as accepted-pending. Unknown/changed write intents and ERP or SKU membership changes retain their original stop rules. The generic binding helper keeps strict conflict stopping by default; only this explicit workflow opts into SPU-level deferral. A changed remote value alone does not identify who changed it or authorize overwriting it.

Cached-first scheduling can put the frozen job order ahead of the original worksheet row order. Batch projection must preserve the existing job order, per-field exclusions and every sibling SKU; it must not rebuild job order from rows and thereby change the task signature. This mismatch was reproduced at the first mixed cached/image-required segment. Fix the projection, not the state hash: retain the original segment plan and seeded images, verify the corrected subset has the same signature, then resume the same directory. Partial or duplicate sibling rows are rejected.

It did not establish completion of all remaining products, short-title writes for a batch without title tasks, or automatic resolution of pre-existing pending audits. ## Explicit resource cooldown

With explicit user authorization, `--resource-cooldown` replaces immediate resource-pause with a bounded recovery episode. After generation threads settle and preserve valid partial output, only the exact rejected request is retried with the same credential and unchanged payload: first after 60 seconds, subsequent attempts after 120 seconds, and no new dispatch at or after 300 seconds from the first resource rejection. Response time counts toward that window; a request already in flight may settle later, which is not an additional retry. A 429 Retry-After longer than the remaining window results in waiting to the deadline without another dispatch. Auth failures, real quota exhaustion and unknown write receipts still stop immediately.

State under `.state/image-resource-recovery` stores the original deadline, probe count, sanitized evidence and request SHA, never the credential or request image data. Recovery probe images are technically decoded, saved with SHA and reused without another image request, including after restart. A probe returning ordinary per-image moderation is cached as that image's failure; `--defer-incomplete` skips it and continues unrelated tasks. No alternate credential, prompt or reference image is used to evade policy. Repeated failures and restart do not reset an unresolved/exhausted episode. A valid cached probe image (or definitive per-image rejection instead of resource rejection) ends and archives that episode immediately, without waiting for the whole generation segment. A later resource block starts a new 300-second window: the stop rule is continuous unavailability, not total segment duration. HTTP200 without a valid decoded image is not recovery. New authorization and an archived prior checkpoint are required to reopen a genuinely exhausted episode. Do not use this opt-in for a permanent ban or an explicit provider instruction not to retry.

`test_resource_cooldown.py` verifies the five-minute deadline, single probe owner, same payload, response-image reuse across restart, ordinary failure skips, quota/auth pauses, cancellation, Retry-After, SHA tampering, route isolation and actual generation integration with a mocked transport.

Recoverable probe transport interruptions and gateway failures retain typed `ModelTransientError` classification. They cool down again within the same original deadline rather than ending the batch prematurely or restarting the five-minute window. Each probe remains a single HTTP attempt; a later deadline check stops genuinely continuous unavailability. This does not retry unknown browser uploads, bindings or title writes.

`run-direct --pipeline` is opt-in and direct-only. It reuses the existing generation, upload, binding and exact readback implementations; it does not change manual or POP routing. Initial scope verification and cache migration for the next segment run on the sole browser thread before its generation starts. Only one next generation future exists; all model calls share the same four-worker limiter and one-start-per-second gate. Uploads, binding and title writes stay serialized on the browser thread. Normal image failures remain skipped under `--defer-incomplete`.

Before prefetching, persist the canonical group and child-plan SHA in `direct-progress.json.prefetchedSegment`. Restart verifies that record and resumes the same group even if batch size changes. Active and prefetched groups never overlap completed/deferred groups; title reservations retain their exact grouping. Unknown writes, scope changes and failed native reads still stop the writer; shutdown cancels new model dispatch, drains in-flight requests under the execution lock, then closes the shared client. Cancelled images are not saved as permanent image failures. Resource/authentication/quota errors keep their existing evidence and pause semantics. Do not automatically rotate credentials or retry a blocked resource.

`--cached-only` disables lookahead and all model calls. To return to serial execution, omit `--pipeline`; reserved groups are still honored. Do not delete the prefetch marker, frozen plan, partial images or pending write receipts to resume. The runner records `.state/run-events` and each segment's `.state/phase-events`, including start/end/error type for interrupted generation. `lastRun.wallSeconds` is the throughput denominator. A prefetched segment's `stageSeconds.generation` may overlap the preceding segment's delivery; neither phase sums nor sums of segment elapsed times represent overall wall time.

Offline regression: `test_direct_pipeline.py`, `test_direct_material_failures.py`, and existing exclusion, quota, skip and unknown-write suites. Validate a bounded two-segment live run before scaling. Offline overlap is not evidence that the provider remains available or that product fields were written.
