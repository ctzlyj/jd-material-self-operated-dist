# Explicit unknown-upload quarantine

Use only when an exact image-space upload remains uncertain after native read-only reconciliation and the user explicitly authorizes isolating its entire SPU while other original products continue. A missing search result does not prove no write occurred. Ordinary failure skipping, generation authorization or a request to continue does not authorize this exception.

At a settled checkpoint, verify the actual worker has exited and no unrelated execution lock remains. Use `quarantine-upload --erp <original-erp> --output-dir <original-direct-run> --confirm-token <original-direct-token> --segment-id <original-segment> --spu-id <authorized-spu> --file-name <original-name> --confirm ISOLATE_SPU_WITHOUT_REPLAY`. This performs local audit writes only: archive the original task and upload ledger bytes, bind the original master/segment plans and complete SKU membership, and freeze image/reference SHA values. It never uploads, changes the old receipt to success, edits the source plans, or expands the ERP.

Continue the same `run-direct`, including its original cache, frozen group and prefetched segment. The exact frozen unknown entry is exempted from the stop gate, not deleted or reconciled. The whole SPU is excluded from reference downloads, text/image generation, uploads, material binding and title writes. It stays in the original group and full-SKU failure list as `quarantined-unknown-upload`; final readback handles only non-quarantined deferred work and cannot promote it. Finalizing a queue with only this item left does not query all deferred items through an empty-selection fallback. Use `run-direct`, not `run-titles`, while quarantine exists.

The frozen entries, companion URLs, per-SPU state, images, ERP and SKU scope must remain unchanged. A changed receipt/image/state, a new unknown upload, unknown binding/title write, identity error or scope expansion stops normally. No automatic quarantine of subsequent failures, credential rotation, rename, generation retry, blind reupload or marking all products complete is allowed.

Multiple explicitly authorized SPUs can be appended in the same original task. Show the exact SPU, complete SKU membership and all its current unknown filenames before obtaining whole-SPU isolation authorization. Repeat the command for each authorized SPU, using one of its original unknown filenames as the anchor. Each activation freezes every currently unknown upload of that SPU, not just the anchor. The immutable v2 record references the previous evidence by SHA; original v1 single-SPU records remain valid and unchanged. Never replace an older target, reset the pointer, or authorize future unknown SPUs implicitly. Repeating an already frozen filename is idempotent; later changed/new entries still fail closed. Each record validates before pointer activation, under the original execution locks.

An older installed client with the single-target restriction is a local implementation gap, not an ERP authorization restriction. Follow `autonomous-recovery.md`: reproduce it with synthetic records, repair the local quarantine collection and all its consumers, verify legacy compatibility and no-replay guards, then apply non-destructively at a settled checkpoint. Do not delete the old guard without implementing those protections, wait repeatedly for a release, or use a maintenance request as isolation consent.

There is no automatic release or replay of quarantine. A future recovery needs reliable exact server evidence and a separately verified state transition preserving the original evidence. Do not delete the pointer to bypass protection. If activation validation fails, preserve all archived bytes and stop for inspection. Roll back code only at a settled checkpoint through the non-destructive installer; the old unknown-write gate will stop this task until handled safely.

Verification: `tests/test_upload_quarantine.py` and `tests/test_multiple_upload_quarantines.py` cover legacy and appended isolation, multiple unknown images, default/new-unknown stops, changed SHA/receipt rejection, validation before activation, full-SKU failure export, zero generation for held SPUs, upload/binding/title entrypoint guards, continuation of the original group and final-readback non-promotion. Full release tests, clean installation, installed-runtime SHA checks and a real original-segment continuation are required before claiming production recovery. This fixes task isolation, not the unknown upload's provider root cause or proven throughput.
