# Bounded image-key comparison

Only compare multiple separately authorized runtime credentials after the production writer settles and its execution lock is released. Use real missing image slots from the unchanged authorized plans. Never regenerate valid images to make a sample, change a rejected request's credential, or expand product ownership. Production dual-key scheduling is not enabled by this diagnostic module; separately authorized production uses `dual-key-generation.md`.

Single-key four-way and two-key two-way samples share one total semaphore of four and the same one-start-per-second gate. Each dual round reserves exactly two requests for each key; drain all in-flight requests before recovery or the next round. Balance image kinds, alternate order when enough real missing slots exist, and separate cold initialization from model wall time. A small unpaired pilot, a run interrupted for a code repair, or a successful secondary-key image does not establish a production speed gain.

Use `scripts/image_benchmark_metrics.py` for attempt identity, exact event correlation, cancellation classification, bounded retry timing and final attempt totals. Windows `time_ns()` values can coincide across worker threads: use `new_attempt_id()` and correlate both the attempt and exact task. Preserve historical raw events before correcting old timer collisions; never rewrite them as if the initial statistics had been correct.

HTTP response hooks observe headers before the full image body has necessarily arrived. HTTP 200 with a later transport exception is not successful image generation. Count actual HTTP starts, HTTP error statuses, failed image attempts, valid saved images and cancelled-before-dispatch tasks separately. Recovery successes are new attempts but only one valid output for that task. Persist error evidence with the existing credential/image-data redactor; do not store headers, keys or raw image request payloads in metrics.

Native key-throttling code 2008 is distinct from exhausted-quota code 2007. Neither label is inferred from HTTP 429 alone. A resource/key throttle can use only the already authorized same-key, unchanged-request recovery policy. For explicitly authorized thirty-minute recovery, keep the original first failure and deadline, wait five minutes and then ten minutes, respect longer Retry-After values, and serialize probes. A transient body/transport failure can continue within that original window; it must not reset the clock or be mistaken for successful recovery. Authentication, real quota exhaustion, content rejection and unknown product writes retain their safety stops.

Measure recovery time on success, cancellation, exhaustion and error exits, not only the happy path. Preserve interrupted probe receipts and their SHA values before resuming. Revalidate the original ERP, current complete SKU scope, reference SHA and unchanged prompt/request hash. A recovered valid image stays cached and must be reused by normal maintenance.

Decide on production use only after comparable repeated rounds establish successful throughput, failure rate and recovery cost without relaxing the global limits. Do not infer a multiplier by dividing a stable dual round by a single-key round that includes operator repair time. If evidence is incomplete or unstable, leave the production default unchanged and report why.

Regression: `tests/test_image_benchmark_metrics.py` covers timer collisions, exact-task isolation, zero-dispatch cancellation, immutable recovery deadlines, transient HTTP-200 body failure, hard-stop precedence and separate wire/image outcome counts. These are offline diagnostic proofs, not platform throughput or audit approval.
