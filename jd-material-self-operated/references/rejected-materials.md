# Rejected material maintenance

## Default: skip and deliver appeal evidence

Native rejection or a definitive generation/upload failure is a skipped, unfinished SPU, not an automatic repair request. Continue other authorized products without regenerating images, changing filenames, retrying uploads/binding or altering categories. Preserve all sibling SKUs, valid files, URLs and immutable receipts. Deliver SPUID, SKUID, failure stage, exact native reason and evidence SHA for colleague appeal; distinguish title category/attribute errors from image rejection and accepted-but-unmatched values. Unknown writes still stop for reconciliation; this policy does not authorize new quarantine or replay.

First-use discovery retains rejected SPUs in its frozen original plan and full-SKU failure list, but holds them before any generation, upload, binding or title write. `maintain-self-operated --regenerate-rejected-spu-ids <IDs>` is only for an explicit, targeted correction request. IDs must be discovered rejected products, are bound into the plan hash and cannot be added on resume. Preserve the old task when creating a separately authorized correction plan. Existing-task deferrals and source-image failures must not be cleared to manufacture a fresh attempt.

The repair techniques below apply only after that specific request. No meaningful correction or another rejection means skip again, not a repair loop. Source-level and actual-runner regressions cover default zero-write skip, explicit repair, frozen authorization, complete sibling lists and native failure reasons.

The local cutout preserves valid approved white JPEG bytes instead of whitening or recompressing them. New white-image normalization no longer turns every near-white subject pixel into pure white. Edge-connected background removal uses the conservative near-white threshold (all channels at least 248, channel spread at most 8) rather than the old 225/36 flood fill that erased light product edges. Regression tests cover light subjects touching the background, white normalization and exact-byte approved-image restoration. Preserve the old rejected image and compare source/output hashes when repairing it; these pixel-processing checks are not semantic review or a guarantee of platform approval. If no meaningful correction is available, defer the affected material rather than rename and resubmit it.

To check whether a formerly accepted/completed checkpoint was rejected later, use `scripts/direct_reconcile.py --include-completed --spu-ids <recorded IDs>` with the original ERP, output and confirm token. It reads the current audit for completed as well as deferred records, preserves source receipt hashes, returns `auditRejectedSpuIds`, and never mutates old progress or writes product fields. The default remains deferred-only. Do not interpret the old completed checkpoint as current approval after a later rejection; use the new readback as repair evidence and retain the historical receipt.

The native material detail uses status 4 for approved, 3 for pending and 5 for rejected. Binding reconciliation also recognizes its status-2 rejection representation. A previous upload, accepted binding receipt or high cached score cannot override rejection. Preserve raw reasons, URLs, all sibling SKU IDs and source hashes. Discovery records `rejectedMaterials`, `rejectedSpus` and `rejectedSkus`; rejection blocked by a pending sibling stays in the final failure/pending list instead of disappearing as nothing to maintain.

For specifically authorized repairs, reuse the existing direct workflow rather than an alternate writer. Only the requested rejected slots enter correction even if the displayed score is qualified. Approved, shared companion URLs remain reusable: transparent-only repairs can restore the approved white image and produce a local transparent derivative without another model call. One rejected scene does not discard its approved companion. Keep full SPU SKU coverage; do not fabricate a shared approved URL when siblings differ. Inspect such differences before any replacement rather than shrinking the SKU set.

Before binding, requery native materials. A proposed value that matches a rejected value for any affected SKU is not resubmitted, even when this computer lacks the original acceptance receipt. A corrected new value can be planned through the normal request hash, pre-write full-scope check, durable intent and exact readback. Approved targets and exact pending targets are not submitted again. Unknown prior intents still require reconciliation; rejection is not permission to erase them or blindly retry.

For a rejection such as damaged cutout, generating the same alpha mask again or merely renaming the file is not a correction. Diagnose and verify the image-processing change before another production submission; preserve the rejected original and every valid unrelated image. Do not add a semantic/visual model audit or switch credentials, category or prompts around platform controls. A successfully encoded PNG alone does not prove that the platform will accept the cutout. The current automated cutout implementation is not guaranteed to correct every damage rejection.

If named products are delegated rather than directly owned, the agent may use `maintain-self-operated --include-delegated --target-spu-ids <explicit IDs> --plan-only` after the user authorizes those products. The option requires one to fifty IDs and the verified current ERP; a missing native result stops discovery. The SHA-bound plan records `selected-permission-erp-v1` and the selected IDs, without impersonating another ERP or rebuilding an old task. Remove `--plan-only` only within the existing generation/upload/binding authorization and after the replacement is genuinely ready. For larger authorized lists, keep disjoint explicit groups and a parent source manifest; never use an unfiltered all-visible scan as authorization. Existing production exclusions and unknown receipts continue to apply.

Report API accepted, exact readback, pending audit, approved audit, rejected audit and score refresh separately. `auditApproved`, `auditPending` and `auditRejected` in material checks describe native observations; `persisted` or a runner completion checkpoint is not final score acceptance. Re-read later audit results using the existing read-only reconciliation path; do not claim an asynchronous review has completed or automatically loop on rejected replacements.

Verification: `test_rejected_material_repair.py` covers native rejection metadata, pending-sibling retention, approved companion reuse, model-free transparent derivation, an actual-runner synthetic replacement limited to type 36 and every sibling, old rejected value anti-replay, changed replacement planning, explicit delegated scope, identity failure and scope-stable resume. These tests prove workflow behavior, not real audit approval or cutout quality.
